# Архитектура билетов: принятые решения и границы MVP

Целевой продукт — мобильное приложение для Android и iOS. Пользователь
подтвердил два режима одного демонстрационного приложения: выпуск билета
и контроль входа. Общая логика — C++, общий интерфейс — Qt Quick/QML.

Текущее состояние: UMIT 0.3, локальные билеты и аккаунты, интерфейс Qt Quick,
подключение Phantom и чтение баланса Devnet. Android APK для armeabi-v7a
собран; desktop-тесты ядра, кошелька, настроек и аккаунтов пройдены.
Полный сценарий с Phantom на телефоне и сборка iOS ещё не подтверждены.
Solana программа ещё не написана и не развёрнута. Разделы ниже описывают
целевую архитектуру блокчейн-этапа, а не уже работающие транзакции.

## 1. Что в исходной идее хорошо

- Интерфейс отделён от правил выпуска и погашения.
- Проверка «ещё не использован» и изменение `used` образуют одну операцию.
- Локальный прототип позволяет проверить правила до изучения Rust и сети.
- Для демонстрации предусмотрены как успешный проход, так и повторный.

Важное уточнение: «один билет нельзя погасить дважды» не означает
«его нельзя продать двум людям». Можно продать одну картинку нескольким людям;
первым войдёт тот, кто первым успешно предъявит её. Пока это билет на предъявителя.

## 2. Главные проблемы и приоритеты

| Проблема | Последствие | Решение для MVP | Приоритет |
|---|---|---|---|
| Правила только на клиенте | Клиент можно обойти прямым запросом | Проверки в Solana Program | CRITICAL FOR MVP в Devnet |
| Нет авторизации выпуска | Посторонний выпускает билеты | Подпись организатора соответствующего события | CRITICAL FOR MVP в Devnet |
| Нет авторизации погашения | Посторонний заранее гасит чужие билеты | Отдельный разрешённый ключ сканера | CRITICAL FOR MVP в Devnet |
| Не проверяется мероприятие | Билет события A принимают на B | Сравнение с событием, настроенным на сканере | CRITICAL FOR MVP |
| Сброс used при повторной инициализации | Использованный билет становится новым | Запрет переинициализации/закрытия/повторного выпуска по тому же адресу | CRITICAL FOR MVP в Devnet |
| Ответ RPC принят за успех | Вход разрешён без погашения | Проверка результата своей транзакции | CRITICAL FOR MVP в Devnet |
| ID из публичного реестра принят за секрет | Можно предъявить чужой существующий ID | Явно ограничить ID-only демо; перед реальным использованием усилить предъявление | CRITICAL FOR MVP: честные границы |
| Копия QR приходит первой | Настоящему покупателю откажут | Статический QR не решает; позднее доказательство владения | CAN BE FIXED LATER для закрытого демо |

Stage 1 предполагает доверенный вызов внутри одного процесса. Это не имитация
криптографической авторизации. Внешние запросы появятся только вместе с
проверкой полномочий. Ключ организатора не размещаем на сканере.

## 3. Что хранится в Solana

Предлагаемый первый blockchain MVP: входные билеты без нумерованных мест,
без продажи внутри программы и без передачи между владельцами.

| Объект | Поля бизнес-состояния | Назначение |
|---|---|---|
| Event account | `organizer_authority`, `scanner_authority`, `max_supply`, `issued_count` | Кто выпускает, кто гасит, сколько разрешено выпустить |
| Ticket account | `event`, `used` | К какому событию относится и погашен ли |

ID билета — адрес его аккаунта. Технический формат также потребует идентификации
типа/версии данных; bump и отдельный исходный идентификатор для PDA добавляем
только если это понадобится выбранной схеме адресации и проверок.

`created_at` не нужен для одноразового входа. Публичный ключ посетителя имеет
смысл добавлять вместе с проверкой владения этим ключом, а не заранее.
Поле `owner` самого Solana account — программа, управляющая его данными,
а не покупатель. Код программы и данные билетов — отдельные аккаунты.
[Официальное устройство аккаунта](https://solana.com/docs/core/accounts/account-structure).

Для предсказуемого адреса можно использовать PDA: адрес, вычисляемый из
идентификатора программы и исходных значений, например события и ID билета.
У него нет собственного приватного ключа. Вычисление адреса ещё не создаёт
аккаунт и не заменяет проверку прав. Подробную схему и сериализацию выберем
на этапе программы. [PDA](https://solana.com/docs/core/pda).

Изображения, названия, контакты и секреты посетителей не помещаем в публичное
состояние. Это не требуется для погашения; данные и транзакции доступны для чтения.

`max_supply` задаётся при создании события; в MVP не предусматриваем его увеличение.
`create_ticket` проверяет лимит и увеличивает счётчик вместе с выпуском.
Это ограничивает число билетов этого события, но не доказывает реальную
вместимость зала и не запрещает мошеннику создать другое событие.

## 4. Что остаётся в C++ и кому доверяем

```text
Организатор: C++ выпуск + его отдельный ключ
                  |
                  v
              Solana RPC -> Ticket Program -> Event / Ticket accounts
                  ^
                  |
QR -> C++ сканер + ключ сканера -> отправка use_ticket
                  |
          проверка своей транзакции
                  |
       успех с нужным подтверждением -> ACCESS GRANTED
       отказ программы             -> ACCESS DENIED + причина
       результат пока неизвестен   -> PENDING, вход закрыт
```

| Компонент | Принимает → возвращает | Где работает; доверие и последствия взлома |
|---|---|---|
| C++ выпуск | Событие → запрос выпуска, ID, QR | Приложение организатора; украденный ключ даёт его полномочия |
| QR-декодер | Изображение → данные билета | Сканер; ограничиваем формат/размер и проверяем данные |
| C++ сканер | Билет + настроенное событие → результат прохода | Устройство входа; скомпрометированный ключ может гасить билеты своего события |
| RPC | Запрос чтения или подписанная транзакция → данные/статус | Сетевой узел; может задержать или исказить ответ клиенту, сам по себе не может подделать подпись |
| Ticket Program | Инструкция + аккаунты + полномочия → новое состояние или ошибка | Solana; ошибка проверки или вредоносное обновление может нарушить правила |
| Локальное управление входом | Подтверждённая операция → действие устройства | Сканер/турникет; физический проход не является частью blockchain транзакции |

Адрес программы, сеть, допустимое событие и RPC задаёт конфигурация сканера.
QR не должен подменять их произвольными адресами/URL. Имя события из QR — не
доказательство его подлинности. Нужна привязка к доверенному организатору.

Отдельный Rust-клиент или FFI слой пока не добавляем. На интеграции сравним
прямую работу C++ с проверенной библиотекой и маленький адаптер на официальном
SDK. C++ остаётся основным приложением; самописную криптографию не делаем.

## 5. Минимальный MVP и порядок работ

1. **Stage 1, готово:** локальные структуры, выпуск, проверки, погашение, гонка.
2. **Мобильная оболочка и QR:** сборка двух режимов Qt Quick на Android/iOS,
   затем версия формата, ID, генерация QR и чтение камерой; пока один сеанс.
3. **Минимум Solana/Rust:** аккаунт, инструкция, транзакция, подпись, PDA, Result.
4. **Program + локальные тесты:** `create_event`, `create_ticket`, `use_ticket`,
   права организатора/сканера, лимит, связь с мероприятием и запрет сброса used.
5. **Devnet:** развёртывание, тестовые средства, настоящий выпуск/погашение.
6. **C++ интеграция:** чтение, отправка, статусы, подтверждения и восстановление
   после неопределённого результата.
7. **Демо:** первый проход, повтор, чужое событие, два сканера, сетевой сбой.
8. **Усиление:** доказательство владения, transfer, ключи устройств, аудит,
   сохранение журнала физических действий и работа при отказах.

Первый завершённый Solana MVP — закрытое Devnet демо с одним событием и одной
ролью сканера. Для двух независимых устройств позже выдаём отдельные ключи
с отдельными разрешениями и отзывом доступа. Реальные продажи в него не входят.

Наличие обеих вкладок в одном демо не заменяет авторизацию: перед Devnet
выпуск потребует ключа организатора, а контроль — отдельного ключа сканера.
Нельзя прятать переключатель роли и считать это защитой полномочий.

Qt Quick описывает экраны в QML и вызывает `TicketController` на C++.
Этот адаптер передаёт ID строками (чтобы сохранить полный uint64), вызывает
`TicketManager` и сообщает результат интерфейсу. Сейчас оба режима используют
один менеджер на одном телефоне. Локальный менеджер каждого телефона не может
разрешать общий вход независимо — окончательное состояние перенесём в Solana.
Между Android и iOS общие исходники, но разные сборки и проверки устройств.

## 6. Почему два погашения не проходят

`verify_ticket` как отдельная транзакция не нужен: интерфейс может читать данные.
`use_ticket` обязательно заново проверяет всё внутри изменения состояния:

```text
проверить ожидаемый тип, адрес/PDA и owner переданных accounts
проверить подпись и полномочия сканера для Event
проверить Ticket.event == ожидаемый Event
проверить Ticket.used == false
записать Ticket.used = true
```

Ticket объявляется writable. Обе попытки должны обращаться к одному аккаунту
этого билета. Конфликтующие изменения согласуются средой исполнения; вторая
выполнившаяся после первой операция увидит used=true. Ошибка отменяет изменения
состояния инструкций транзакции; комиссия при исполнении с ошибкой может
сохраниться. Это похоже на защищённую транзакцию БД, а не на mutex между
двумя приложениями. [Атомарность](https://solana.com/docs/core/transactions),
[исполнение и конфликты](https://solana.com/docs/core/transactions/transaction-pipeline).

Точная гарантия: не более одного успешного погашения в согласованном состоянии.
Доставка не гарантирована: обе попытки могут не попасть в сеть. Вторая попытка
может получить сетевую ошибку вместо `ALREADY_USED`.

При погашении Event нужен только для чтения. Не увеличиваем в нём общий
счётчик проходов — он сделал бы все билеты общим местом конкуренции за запись.
Отдельные билеты уменьшают такие конфликты, но общий fee payer также может
ограничивать параллелизм. Оптимизация этого места не нужна Stage 1.

## 7. Отправка, подтверждение и физический вход

RPC — удалённый интерфейс узла: технически запросы чтения и отправки транзакций.
В проекте C++ через него узнаёт состояние билета и отправляет `use_ticket`.

Транзакция — подписанный запрос изменений, технически набор инструкций и
необходимых данных. В проекте сканер подписывает попытку погасить конкретный
билет. Подпись подтверждает полномочия ключа, но не шифрует содержимое QR.

`sendTransaction` возвращает идентификатор принятой транзакции, а не разрешение
на проход. Сохраняем подписанную попытку/её signature, затем проверяем именно
её результат: `err == null` и нужный уровень подтверждения.
[sendTransaction](https://solana.com/docs/rpc/http/sendtransaction),
[getSignatureStatuses](https://solana.com/docs/rpc/http/getsignaturestatuses).

Для первой демонстрации строгого свойства выбираем `finalized`. `confirmed`
можно выбрать позднее ради меньшего ожидания, явно приняв остаточный риск
отката. `processed` для открытия входа не используем.
[Уровни подтверждения](https://solana.com/docs/rpc#configuring-state-commitment).

Таймаут означает неизвестный результат. Сначала восстанавливаем статус прежней
попытки; при истечении её срока учитываем статус и актуальное состояние прежде,
чем формировать новую. `used=true` сам по себе не доказывает, что победил наш
сканер. Повторно полученный успех одной signature не должен давать второй проход.

Для реального турникета понадобится долговечный журнал операций, идентификатор
команды и дедупликация со стороны контроллера. Падение между погашением и
открытием — отдельная задача восстановления. Blockchain гарантирует изменение
реестра, а не ровно одно механическое открытие. В демо показываем результат
в консоли. При отсутствии связи держим вход закрытым и показываем состояние
связи; обычный офлайн-кеш не защищает от входа через два несвязанных сканера.

## 8. Что дают разные способы защиты QR

| Способ | Что защищает | Чего не защищает | Сложность; когда |
|---|---|---|---|
| Случайный ID/nonce из CSPRNG | От угадывания непубличного значения | От копирования и чтения ID из публичного реестра | Низкая; с настоящими ID, не считать секретом on-chain |
| Secret в QR | От знания только публичного ID, если secret нигде не раскрыт | От копии QR; раскрытый secret перестаёт помогать | Средняя; позже вместе с безопасным протоколом предъявления |
| Hash secret в состоянии | Не раскрывает сильный secret прямо в аккаунте | Не решает перехват раскрываемого secret и копирование | Средняя; позже, не отправлять раскрытие без привязки к попытке |
| Digital signature / signed payload | Подтверждает подписанта и неизменность полей QR | Не защищает подписанную картинку от копирования | Средняя; после простого QR, перед заявлениями о защите предъявления |
| Expiration time | Ограничивает срок пригодности | Не мешает копированию внутри срока; неподписанный срок изменяем | Низкая как часть проверяемого payload; позже |
| Dynamic QR | Сокращает время использования старого скриншота | Не блокирует быструю пересылку/relay | Средняя/высокая; позже |
| Wallet ownership | Позволяет проверять право владельца ключа | Само поле owner ничего не доказывает; не исключает кражу/передачу ключа | Средняя/высокая; вместе с доказательством подписи |
| Challenge-response | Подпись свежего одноразового вызова связывает предъявление с попыткой | Не доказывает физическую личность/близость; возможен live relay | Высокая; позже, привязка к билету, событию, сканеру и сроку |

Ни QR, ни подпись не предотвращают произвольную продажу картинки вне системы.
Защита перепродажи потребует управляемого transfer и согласования оплаты с
передачей прав. NFT не обязателен для текущих операций; совместимость с
чужими кошельками не возникает автоматически у собственного формата аккаунтов.

## 9. Нужен ли blockchain

Для одного организатора и доверенного сервера БД проще. Условное обновление:

```sql
UPDATE tickets SET used = TRUE
WHERE id = :id AND event_id = :event AND used = FALSE;
```

Вход разрешается только после успешного COMMIT, если обновилась ровно одна
строка. Проверка полномочий и сетевое восстановление нужны и в таком варианте.

Solana оправдана, если несколько независимых участников хотят пользоваться
общими проверяемыми правилами выпуска, передачи и погашения, не делегируя
всё одному владельцу БД. Причина выбора для проекта — изучить и показать эту
модель на аккаунтах и атомарных транзакциях, а не объявить её автоматически
безопаснее или доказанно оптимальной по стоимости и задержке.

Организатор всё ещё может лгать о событии; разрешённый сканер — гасить билеты
без посетителя. Владелец права обновления программы может изменить её правила.
В Devnet сохраняем upgrade authority для разработки и явно раскрываем это.
Для production нужна политика обновлений; заморозка также имеет цену —
невозможность обычного исправления ошибок. [Обновление программ](https://solana.com/docs/core/programs/program-deployment).

Проверяемая история не равна гарантии её бесплатной вечной доступности через
любой RPC: для долгого аудита потребуется источник истории/индексация.
Безопасное хранение ключей, отзыв устройств, мониторинг, нагрузочные измерения
и независимый аудит относятся к подготовке production после рабочего MVP.
